# KOL 外联中台项目规范

> 文档状态：基线版 1.0  
> 适用项目：`kol-outreach`  
> 适用角色：产品、后端、前端、测试、运维、安全及运营人员  
> 最后更新：2026-07-15

## 1. 文档目的

本文档定义 KOL 外联中台的产品边界、技术架构、数据模型、接口、安全、AI、部署、测试和发布规范，作为需求评审、开发实现、代码审查、上线验收和故障处理的共同基线。

本文使用以下约束词：

- **必须**：上线前不可缺少的要求。
- **应当**：原则上必须满足；不满足时必须记录原因、风险和补救计划。
- **可以**：按业务需要选择实现。

## 2. 项目定位

### 2.1 产品目标

本项目是面向 KOL 营销运营团队的外联回信中台，负责同步外部发信平台中的邮件活动和回复，通过 AI 判断合作意向，并为运营人员提供统一的 Hot Lead 看板、会话详情、任务分配和内部备注能力。

### 2.2 核心业务流程

```text
KOL 数据导入
    → 外部发信平台创建并执行 Campaign
    → Webhook 同步已发邮件和回信
    → 消息持久化及幂等去重
    → AI 意向分析
    → 会话状态更新
    → Hot Lead 看板
    → 运营分配、备注和人工跟进
    → 在外部发信平台中实际回复
```

### 2.3 当前产品边界

中台负责：

- KOL 联系人数据的导入、查询和维护。
- Snov Campaign、已发邮件和回信数据的同步。
- 邮件会话归组、幂等去重和状态管理。
- 回信意向识别、评分、摘要和行动建议。
- Hot Lead 筛选、运营分配和内部备注。
- 基础运营统计。

中台当前不负责：

- 直接发送首封外联邮件。
- 直接发送人工回复。
- 邮箱账号、SMTP 或 IMAP 凭据托管。
- 完整 CRM、合同、付款和账单管理。
- 已完成的客户级多租户隔离。

前端必须明确提示实际回复应在 Snov 等发信系统中完成，不得让用户误认为中台已经发送邮件。

## 3. 角色与权限

### 3.1 角色定义

| 角色 | 职责 | 最小权限 |
|---|---|---|
| 管理员 | 系统配置、运营人员管理、外部服务配置、数据修复 | 全局管理权限 |
| 运营人员 | 查看会话、接管线索、添加备注、更新状态 | 业务操作权限 |
| 只读人员 | 查看授权范围内的看板和统计 | 只读权限 |
| 外部服务 | 投递合法 webhook | 仅 webhook 接收端点 |

### 3.2 访问控制要求

- 除 `/health` 和经过独立校验的 webhook 外，所有 API 必须要求身份认证。
- 生产环境不得以“可信网络”为理由关闭身份认证。
- 管理 Snov webhook、同步历史数据、删除 KOL、管理运营人员等操作必须限制为管理员。
- 运营人员只能操作其有权访问的客户或 Campaign 数据。
- 后端必须执行权限判断；前端隐藏按钮不能作为安全控制。
- 认证失败返回 `401`，权限不足返回 `403`，不得在错误信息中泄露账号是否存在。
- 所有写操作应当记录操作人、时间、对象和结果。

当前代码中的公开看板仅可用于本地演示，不符合生产规范。

## 4. 总体架构规范

### 4.1 逻辑架构

```text
浏览器
  │ HTTPS
  ▼
Traefik / Caddy
  ├── Vue 3 静态资源
  └── /api/* → FastAPI
                  ├── PostgreSQL
                  ├── Snov API
                  └── OpenAI API

Snov Webhook ──HTTPS──> FastAPI Webhook Endpoint
```

### 4.2 技术基线

| 层级 | 技术 | 规范 |
|---|---|---|
| 前端 | Vue 3、Vite、Ant Design Vue | 使用 Composition API，API 调用集中封装 |
| 后端 | FastAPI、SQLAlchemy | 路由、服务、模型分层，不在路由中堆积复杂任务 |
| 数据库 | PostgreSQL | 生产唯一标准；SQLite 仅限本地开发和测试 |
| AI | OpenAI API | 使用结构化输出、严格校验、超时和降级机制 |
| 网关 | Traefik/Caddy | 强制 HTTPS、限制请求体、配置安全响应头 |
| 部署 | Docker Compose | 镜像和依赖版本可复现，配置由环境变量注入 |

### 4.3 分层约束

- `api/` 只负责请求解析、权限校验、调用服务和组织响应。
- `services/` 负责外部 API、AI 和核心业务逻辑。
- `models/` 只定义持久化模型和必要关系。
- 长时间同步、批量 AI 分析不得在 Web 请求中直接串行执行。
- 外部服务客户端必须统一处理超时、重试、认证刷新和错误映射。

## 5. 数据规范

### 5.1 核心实体

| 实体 | 用途 | 关键约束 |
|---|---|---|
| `kol` | KOL 联系人主数据 | 规范化邮箱应唯一 |
| `thread` | 按联系人和 Campaign 聚合的会话 | 必须关联 KOL |
| `message` | 收发邮件记录 | 外部消息标识必须幂等 |
| `operator` | 运营人员 | 登录标识应唯一 |
| `note` | 内部备注 | 必须关联会话和操作人 |
| `send_log` | 历史发送或推送记录 | 必须保存供应商和结果 |

### 5.2 字段与一致性要求

- 邮箱写入前必须去除首尾空格并转换为小写。
- 数据库必须为规范化邮箱建立唯一约束；应用层查重不能替代数据库约束。
- 所有外部 ID 必须以字符串保存，不得假设其永远为整数。
- 时间统一以 UTC 存储，API 返回 ISO 8601 时间并带时区。
- 不得通过直接移除 `tzinfo` 的方式处理带偏移时间。
- `message.message_id` 必须具备全局唯一约束；外部未提供 ID 时使用稳定指纹。
- 删除 KOL 前必须定义明确策略：存在会话时拒绝删除、软删除，或经审计后级联删除。
- `thread.status`、`message.direction`、`last_intent` 等枚举字段必须在应用层和数据库层校验。
- 生产数据库结构变更必须通过 Alembic 迁移完成，不得依赖 `create_all()` 升级既有数据库。

### 5.3 会话状态

允许状态如下：

| 状态 | 含义 |
|---|---|
| `open` | 已建立会话，暂无明确高意向 |
| `hot` | 高意向，需要优先跟进 |
| `warming` | 中等意向，需要持续跟进 |
| `cooling` | 低意向或暂缓 |
| `closed` | 拒绝、完成或人工关闭 |

自动回复和外出回复不得自动将会话升级为 Hot Lead。人工关闭的会话不得被旧消息重新打开；新 Campaign 的新回复可以创建新会话。

### 5.4 数据保留与备份

- 生产数据库必须每日自动备份。
- 至少保留 7 个每日备份和 4 个每周备份，具体周期可按业务要求提高。
- 应当定期执行恢复演练，而不仅检查备份文件是否存在。
- 邮件正文属于敏感业务数据，必须规定保留周期和删除流程。
- 日志不得记录完整邮件正文、API Key、密码、OAuth Token 或 webhook token。

## 6. API 规范

### 6.1 路径和版本

- 当前 API 前缀为 `/api`。
- 出现不兼容变更时必须引入 `/api/v2`，不得静默修改现有响应语义。
- 资源使用复数名词，如 `/api/kols`、`/api/threads`。
- 查询使用 `GET`，创建使用 `POST`，局部更新优先使用 `PATCH`，删除使用 `DELETE`。

### 6.2 响应格式

列表接口应统一返回：

```json
{
  "items": [],
  "page": 1,
  "size": 50,
  "total": 0
}
```

错误响应应统一返回：

```json
{
  "code": "RESOURCE_NOT_FOUND",
  "message": "资源不存在",
  "request_id": "..."
}
```

不得把 Python 异常、数据库语句、供应商原始密钥或内部堆栈返回给客户端。

### 6.3 状态码

| 状态码 | 使用场景 |
|---|---|
| `200` | 查询或更新成功 |
| `201` | 资源创建成功 |
| `202` | 后台同步或批处理已受理 |
| `400` | 请求格式错误 |
| `401` | 未认证或凭据无效 |
| `403` | 已认证但无权限 |
| `404` | 资源不存在 |
| `409` | 唯一约束、状态或幂等冲突 |
| `422` | 字段校验失败 |
| `429` | 请求或外部服务限流 |
| `502` | 上游服务失败 |
| `503` | 必要配置缺失或服务暂不可用 |

### 6.4 输入限制

- CSV 上传必须限制扩展名、MIME 类型和文件大小。
- CSV 必须校验表头、邮箱格式、行数和单字段长度。
- 备注、产品描述、邮件正文等文本字段必须设置最大长度。
- 批量接口必须限制单次对象数量。
- 所有排序字段和过滤枚举必须使用白名单。
- 对外部 URL 的输入必须限制协议、域名和用途，避免 SSRF 或数据投递到未授权地址。

### 6.5 幂等性

- Webhook 以外部 `message_id` 或稳定指纹去重。
- 批量同步重复执行不得产生重复消息或重复统计。
- 可能被客户端重试的创建接口应支持 `Idempotency-Key` 或业务唯一键。
- 数据库唯一冲突应转换为 `409`，不得返回未处理的 `500`。

## 7. Snov 集成规范

### 7.1 认证

- `SNOV_CLIENT_ID` 和 `SNOV_CLIENT_SECRET` 只能来自环境变量或密钥管理系统。
- OAuth access token 不得写入数据库或日志。
- 客户端必须跟踪 token 过期时间，并在过期前刷新。
- 收到 `401` 时可以清除缓存 token 并安全重试一次；不得无限重试。

### 7.2 Webhook

- Webhook 必须使用 HTTPS 公网地址。
- 必须在 3 秒内返回 `2xx`，耗时 AI 分析必须在持久化之后异步执行。
- 接收端必须验证独立 token 或供应商签名。
- token 不应出现在普通访问日志中；如必须使用查询参数，网关必须脱敏。
- 必须处理供应商重试，同一事件重复投递不得重复入库。
- 不支持的事件应返回成功并标记为忽略，避免无意义重试。
- 原始 payload 可以短期加密留存用于排障，但必须脱敏并设置保留周期。

### 7.3 历史同步

- 仅同步邮件回复时，应使用邮件回复接口；使用 `all-replies` 时必须区分邮件与 LinkedIn 类型。
- 历史同步必须作为后台任务运行并返回任务 ID。
- 必须按 Campaign 和分页保存同步游标，支持断点续传。
- 单条数据失败不得导致整批回滚。
- 同步结果必须包含新增、重复、跳过、失败和最后同步时间。

### 7.4 定时同步与附件

- 配置 Snov API 凭据后，服务端必须每 120 秒执行一次邮件回复补偿同步。
- 同一时刻最多运行一个同步任务；延迟任务应合并执行，禁止并发重复拉取。
- 前端 Hot Lead 和会话详情页每 120 秒刷新一次，但前端刷新不得替代服务端同步。
- 每封邮件必须保存主题、正文、联系人邮箱和 Campaign 名称（任务名）。
- Snov 当前公开的 Campaign 回复 API未承诺提供附件字段。只有上游真实返回附件元数据时才能保存和展示，不得伪造附件已同步状态。
- 附件元数据仅允许保存标识、文件名、安全 HTTP(S) 下载地址、大小和 MIME 类型；不得把不受控 Base64 文件体写入消息 JSON。
- 业务要求完整获取所有附件实体时，必须增加邮箱侧 IMAP、Gmail API 或 Microsoft Graph 集成及相应授权、病毒扫描和存储策略。

## 8. AI 规范

### 8.1 输出结构

意向分析结果必须符合以下结构：

```json
{
  "intent": "high",
  "intent_score": 85,
  "budget_mentioned": null,
  "key_questions": [],
  "timeline": "flexible",
  "summary": "对方有明确合作意愿并询问价格",
  "suggested_action": "立即跟进"
}
```

约束：

- `intent` 只能是 `high`、`medium`、`low`、`negative`、`ooo`、`auto_reply`。
- `intent_score` 必须是 `0` 至 `100` 的整数。
- 模型输出必须经过 Pydantic 或等价 Schema 校验后才能写入数据库。
- 非法输出最多重试一次，仍失败则进入规则降级并记录失败原因。

### 8.2 状态映射

| 条件 | 会话状态 |
|---|---|
| `high` 或评分不低于 75 | `hot` |
| `medium` 或评分 40–74 | `warming` |
| `low` 或评分低于 40 | `open` |
| `negative` | `closed` |
| `ooo`、`auto_reply` | 保持原状态 |

人工状态的优先级必须高于 AI 自动状态，系统应记录状态来源。

### 8.3 安全与质量

- 邮件正文属于不可信输入，提示词必须明确忽略邮件中的指令。
- 分析前应当尽量去除历史引用、签名、追踪内容和 HTML 噪声。
- 不得把无关个人数据发送给 AI 服务。
- 必须设置请求超时、最大正文长度和最大输出长度。
- 规则降级必须先判断拒绝、退订和自动回复，再判断高意向关键词。
- 应当维护固定标注样本集，持续评估准确率、召回率和误报率。
- AI 判断只用于运营排序，不得作为自动签约、付款或不可逆决策依据。

## 9. 前端规范

### 9.1 页面范围

前端至少包括：

- 总览页。
- Hot Lead 会话列表。
- 会话详情页。
- KOL 列表和导入页。
- 基础统计页。
- 登录和无权限页面。

### 9.2 交互要求

- 所有异步请求必须具有加载、成功、空数据和失败状态。
- 页面加载失败不得永久停留在 Spinner。
- 删除、批量生成、历史同步等操作必须二次确认。
- 后台任务必须展示任务状态，不得通过长时间阻塞按钮等待。
- 列表必须使用服务端分页并展示真实总数。
- 颜色不能作为意向或状态的唯一表达方式。
- 邮件正文默认以纯文本展示；禁止直接渲染未经净化的外部 HTML。
- 复制邮箱等浏览器能力失败时必须提供手工替代方案。

### 9.3 API 客户端

- 统一处理 `401`、`403`、`429` 和 `5xx`。
- 每个请求应携带或接收 `request_id`，便于前后端联合排障。
- 不得在浏览器存储 Snov、OpenAI 或数据库凭据。
- 生产环境 API 必须使用同源 HTTPS 或明确的受信任域名。

## 10. 安全规范

### 10.1 密钥管理

- 真实密钥不得进入源码、Markdown、示例命令、镜像层、前端包或 Git 历史。
- `.env.prod.example` 只能包含占位符。
- 凭据一旦出现在聊天记录、提交记录或日志中，必须视为泄漏并立即轮换。
- 生产密钥应当按环境隔离，开发环境不得使用生产凭据。
- 至少每 90 天审查一次有效密钥和授权范围。

### 10.2 网络与网关

- 生产环境强制 HTTPS，并将 HTTP 重定向到 HTTPS。
- 数据库不得暴露到公网。
- Docker Socket 仅允许只读挂载，并评估 Traefik 对宿主机的权限风险。
- 网关必须设置合理的请求体大小、连接超时和速率限制。
- 应当配置 HSTS、`X-Content-Type-Options`、内容安全策略和点击劫持防护。
- `/docs` 和 `/openapi.json` 在生产环境应关闭或仅管理员可访问。

### 10.3 应用安全

- 所有写接口必须防止未授权访问。
- 对认证接口和高成本接口实施速率限制。
- CSV 导入和 AI 批处理必须设置配额。
- 日志必须脱敏邮箱之外的敏感字段；展示邮箱时按角色决定是否掩码。
- 错误日志可以记录异常类型和 request ID，不得记录凭据或完整请求体。
- 依赖必须定期执行漏洞扫描并及时更新。

## 11. 配置规范

生产环境至少需要以下配置：

| 变量 | 必填 | 说明 |
|---|---|---|
| `DATABASE_URL` | 是 | PostgreSQL 连接地址 |
| `SNOV_WEBHOOK_TOKEN` | 是 | 强随机 webhook 校验值 |
| `SNOV_CLIENT_ID` | 按功能 | Snov 管理和历史同步 |
| `SNOV_CLIENT_SECRET` | 按功能 | Snov 管理和历史同步 |
| `OPENAI_API_KEY` | 否 | 缺失时只能使用规则降级 |
| `CORS_ORIGINS` | 按部署 | 精确允许的前端域名 |
| 认证相关配置 | 是 | 看板身份认证配置 |
| `KOL_PUBLIC_DOMAIN` | 是 | 生产访问域名 |

要求：

- 应用启动时必须校验生产必填配置。
- 不安全的默认密码、空密码和示例 token 必须导致启动失败。
- 启动日志只能显示“已配置/未配置”，不得输出配置值。
- 配置名称、代码读取项、Compose 注入项和示例文件必须保持一致。

## 12. 日志、监控与告警

### 12.1 日志

日志应采用结构化格式，并至少包含：

- 时间、级别、服务名和版本。
- `request_id` 或任务 ID。
- 路由、状态码和处理耗时。
- 外部服务名、调用结果和耗时。
- 业务对象 ID，不记录密钥和完整邮件正文。

### 12.2 指标

至少监控：

- API 请求量、错误率和 P95 延迟。
- Webhook 接收量、重复量、解析失败量和积压量。
- AI 成功率、降级率、耗时和成本。
- Snov API 的 401、429 和 5xx 数量。
- 数据库连接、容量和慢查询。
- 后台任务成功、失败、重试和积压情况。

### 12.3 告警

以下情况必须告警：

- Webhook 连续失败或长时间无事件。
- Snov 认证连续失败。
- AI 降级率异常上升。
- 数据库不可用或备份失败。
- HTTP 5xx 比例超过约定阈值。
- 磁盘空间、数据库容量或任务积压超过阈值。

## 13. 测试规范

### 13.1 单元测试

必须覆盖：

- Snov payload 字段归一化。
- 邮件正文 HTML 清洗。
- 时间和时区解析。
- 消息稳定指纹与幂等逻辑。
- AI 输出校验和状态映射。
- 规则降级中的拒绝、退订、自动回复和高意向场景。

### 13.2 API 集成测试

必须覆盖：

- 未认证访问被拒绝。
- 不同角色的权限边界。
- CSV 正常导入、错误编码、缺失列、超大文件和重复邮箱。
- Webhook token 错误、重复事件、未知事件和缺少邮箱。
- 历史同步重复执行不产生重复消息。
- KOL 删除的关联数据策略。
- 外部服务超时、401、429 和 5xx。

### 13.3 前端测试

应当覆盖：

- 登录和权限跳转。
- 看板筛选、分页和空状态。
- 会话详情加载失败后的可恢复性。
- 分配负责人和添加备注。
- 不在中台实际发信的提示。

### 13.4 上线冒烟测试

每次部署后必须验证：

1. `/health` 正常。
2. 未认证用户无法访问业务 API。
3. 管理员可以登录并查看看板。
4. 测试 webhook 能在 3 秒内得到成功响应。
5. 重复投递同一 webhook 不产生重复消息。
6. 测试回信能够完成 AI 分析或规则降级。
7. 数据库备份任务正常。

## 14. 开发与代码质量规范

- Python、Node 和关键依赖版本必须固定，并提交锁文件。
- Python 代码应通过格式化、静态检查和类型检查。
- 前端代码应通过 ESLint、构建和必要测试。
- 不再使用的 Instantly 或发送逻辑应删除，或明确标记为实验模块并隔离。
- 禁止把异常全部捕获后静默忽略；必须记录可追踪的错误。
- SQLAlchemy 应逐步迁移到 2.x 推荐的 `Session.get()` 和查询方式。
- 单个函数应保持单一职责；大规模同步逻辑应拆分为可测试服务。
- 注释描述必须与实际行为一致，文档不得把计划功能写成已完成。

## 15. 部署规范

### 15.1 环境

至少区分：

- `development`：本地开发，可使用 SQLite 和模拟服务。
- `staging`：与生产相近，用测试账号完成集成验证。
- `production`：PostgreSQL、HTTPS、认证、备份和监控全部启用。

### 15.2 镜像

- 基础镜像必须固定到明确版本或摘要。
- 构建必须使用锁文件，不得每次解析不确定的最新依赖。
- 容器应使用非 root 用户运行。
- 镜像中不得包含 `.env`、数据库、日志、缓存和开发工具。
- 发布前必须扫描高危漏洞。

### 15.3 数据库发布

标准顺序：

```text
备份数据库
  → 执行向后兼容迁移
  → 部署后端
  → 部署前端
  → 冒烟测试
  → 观察监控
```

破坏性迁移必须拆分为多个版本，不得与应用代码同时直接删除仍在使用的字段。

## 16. 发布门禁

生产发布前必须全部满足：

- [ ] 所有业务 API 已启用认证和授权。
- [ ] 已轮换所有曾经暴露的 Snov、OpenAI、数据库及其他凭据。
- [ ] Git 当前版本和历史中不存在有效密钥。
- [ ] 已建立 Alembic 迁移并在 staging 验证升级和回滚。
- [ ] Snov OAuth token 可以自动刷新。
- [ ] Webhook 幂等、3 秒响应和异步分析已经验证。
- [ ] 历史同步不在 HTTP 请求中执行长时间串行任务。
- [ ] KOL 邮箱唯一约束和删除策略已经落实。
- [ ] 后端、前端和集成测试通过。
- [ ] 依赖版本已锁定，生产镜像可复现。
- [ ] HTTPS、备份、监控和告警正常。
- [ ] 隐私、退订和数据保留流程已确认。
- [ ] 已准备回滚步骤和故障联系人。

任一安全、密钥、数据迁移或备份门禁未满足时，不得上线。
