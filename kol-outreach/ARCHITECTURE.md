# KOL 外联中台 · 架构文档

> 本文只讲**架构**：分层、模块职责、数据模型、运行时模型、端到端流程、外部集成方式、部署与安全。
>
> 约定：本文不引用任何**第三方服务的固定字段名**（外部邮件平台的配置键、事件名、列名；外部 AI 服务的密钥名、模型名、请求参数等），统一以"外部 XX 系统 / 适配层 / 配置项"等抽象表述替代。具体字段名请查阅代码与各模块文档。

## 1. 系统概述

### 1.1 系统定位

KOL 外联中台是一套面向运营人员的 **KOL（关键意见领袖）外联协作中台**。它本身**不发信、不直接触达 KOL**，而是承担三类职责：

1. **数据汇聚**：把多来源的 KOL 候选数据汇集、去重、结构化入库。
2. **会话同步与意向研判**：把外部邮件平台的发信 / 回信事件同步进来，用 AI 对回信做意向分级。
3. **运营协作**：在 Web 看板上呈现 Hot Lead、分派、备注、画像回填、报价导出，辅助人工跟进。

### 1.2 系统边界

```
        ┌─────────────────────────────────────────────────────────┐
        │                      外部世界                           │
        │                 ┌──────────────┐   ┌────────────┐       │
        │                 │  外部邮件    │   │  AI 推理   │       │
        │  外部数据文件   │  平台        │   │  服务      │       │
        │  （Excel 上传） │              │   │            │       │
        │      │          └──────┬───────┘   └─────┬──────┘       │
        └──────┼──────────────────┼─────────────────┼────────────┘
               │ 文件上传          │ webhook + 轮询  │ API 调用
               ▼                  ▼                 ▼
        ╔═══════════════════════════════════════════════════════╗
        ║              KOL 外联中台（本系统）                    ║
        ║  ┌─────────┐  汇聚 → 结构化 → 同步 → 研判 → 看板 → 导出║
        ║  │ 采集器  │→ 候选大库 → 发信池                       ║
        ║  │(内嵌爬虫)│  (关键词发现 + 多平台扩展 + 邮箱 + MX)   ║
        ║  └─────────┘                                          ║
        ╚═══════════════════════════════════════════════════════╝
                  ▲
                  │ Web UI
        ┌─────────┴─────────┐
        │   运营人员（浏览器）│
        └───────────────────┘
```

**关键边界原则**：本系统是**研判 + 协作 + 采集**的"中台"，不是发信执行端。所有真实邮件往来发生在外部邮件平台；运营在中台完成研判后，回到邮件平台人工回复。采集能力内嵌于本系统（见 [§6.1](#61-数据入库漏斗候选--发信池)）。

### 1.3 核心价值

- 把运营从"逐封读回信"解放为"只看高意向 Hot Lead"。
- 把多来源、异构、含噪的 KOL 名单收敛为结构化、可去重、可追溯的发信池。
- 让一次性的 Excel 名单沉淀为长期可挖掘的"大数据库"。

## 2. 架构原则与约束

| 原则 | 落地 |
|---|---|
| **中台不执行发信** | 本系统无发信动作；只同步、研判、协作。发送安全阀等配置仅作约束留存 |
| **单一写入闸** | 外部事件入口（webhook）是系统唯一受鉴权保护的写入路径，其余看板接口默认公开 |
| **幂等优先** | 所有外部事件处理、后台任务都按稳定指纹去重，重启可重跑不产生脏数据 |
| **外部依赖可降级** | AI 服务缺失 / 失败时降级为本地规则或占位结果，系统保持可用 |
| **适配层隔离** | 第三方系统（邮件平台、AI 服务）的协议细节封装在适配层，不泄漏到领域层 |
| **结构变更受控** | 数据库结构演进必须走迁移工具，禁止运行时建表 / 手写 DDL 上生产 |
| **进程内任务** | 不引入消息队列；后台任务在进程内完成，靠幂等性兜底重启丢失 |

## 3. 逻辑架构（分层）

### 3.1 后端四层模型

```
┌──────────────────────────────────────────────────────────┐
│  接口层（API / 路由）    backend/api/                     │
│  职责：HTTP 入参出参、鉴权闸、任务编排、BackgroundTasks   │
│  约束：不写业务逻辑，复杂逻辑下沉到服务层                 │
├──────────────────────────────────────────────────────────┤
│  服务层（领域逻辑）      backend/services/                │
│  ├─ AI 研判服务：意向分类 / 内容生成 / 画像抽取           │
│  ├─ 外部邮件平台适配：客户端 / 联系人同步 / 调度          │
│  ├─ 采集器：关键词发现 / 多平台扩展 / 邮箱 / MX / 入库   │
│  ├─ 导出服务：报价工作簿生成                              │
│  └─ 辅助：附件 / 正文处理                                 │
├──────────────────────────────────────────────────────────┤
│  数据访问层（ORM）       backend/models/ + backend/db.py  │
│  职责：领域模型定义、会话工厂、建表/补列（仅遗留兼容）    │
├──────────────────────────────────────────────────────────┤
│  基础设施层              backend/config.py + migrations/  │
│  职责：配置加载、迁移治理、运维 CLI（backend/scripts/）   │
└──────────────────────────────────────────────────────────┘
```

### 3.2 分层依赖规则

- **上层依赖下层，下层不反向依赖**：API → 服务 → 模型 / 数据访问。
- **领域层不感知协议细节**：`models/` 不含任何第三方字段解析逻辑；外部协议字段的解析（事件名、列名、回信格式）一律在服务层的适配模块内完成。
- **运维 CLI 与 HTTP 共用同一服务入口**：导入脚本暴露统一的 `run_import(...)` / `run_backfill(...)` 函数，CLI 和 API 端点都调它，避免两条代码路径分叉。

### 3.3 模块职责矩阵

| 层 | 模块组 | 职责 | 备注 |
|---|---|---|---|
| 接口 | KOL 路由 | 名单列表 / 详情 / 多格式导入 / 开场白生成 | |

| 接口 | 邮箱路由 | 会话邮箱视图（folder / 搜索 / 过滤 / 已读 / 星标 / 分页） | 复杂子查询 |

| 接口 | 邮件平台管理路由 | 连接自检 / 活动 / webhook / 联系人同步 / 历史回信补拉 | 自检不返回密钥 |

## 4. 数据架构

### 4.1 领域模型（9 张表）

系统围绕"**候选 → 发信池 → 会话 → 研判 → 协作**"的漏斗组织数据：

```
   ┌────────────────────┐
   │   候选大库          │  全量候选（含无邮箱），独立池，无外键
   │   (candidate)      │  UNIQUE(平台, 账号)
   └─────────┬──────────┘
             │ 有邮箱才晋升（去重）
             ▼
   ┌────────────────────┐        ┌────────────────────┐
   │   发信池 (kol)      │◀─1:N──│   多邮箱            │  一 KOL 多邮箱
   │   有邮箱的 KOL      │        │   (kol_email)      │  主邮箱镜像回 kol 兼容旧逻辑
   └─────┬──────┬───────┘        └────────────────────┘
         │ 1:N  │ 1:N
         ▼      ▼
   ┌──────────┐ ┌──────────────────┐
   │ 项目评估  │ │ 会话 (thread)     │  status / 意向 / 评分 / AI 摘要
   │ (多项目)  │ │ UNIQUE(项目,KOL) │  FK → kol, FK → operator(分派)
   └──────────┘ └────┬────────┬────┘
                       │ 1:N    │ 1:N
                       ▼        ▼
                ┌──────────┐ ┌──────────┐
                │ 单封邮件  │ │ 内部备注  │
                │(message) │ │  (note)  │
                │ 含 AI 分析│ └────┬─────┘
                └──────────┘      │ FK
                                  ▼
                          ┌──────────────┐
                          │ 运营人员      │
                          │ (operator)   │
                          └──────────────┘

   ┌──────────────┐
   │ 发送审计      │  N:1 kol / N:1 thread（审计用）
   │ (send_log)   │
   └──────────────┘
```

| 表（领域名） | 角色 | 关键约束 |
|---|---|---|
| 候选大库 | 爬虫全量候选池，含无邮箱账号 | 按平台 + 账号唯一 |
| 发信池（KOL） | 有联系邮箱、可被邮件平台触达的集合 | 主邮箱非空、索引、大小写不敏感唯一 |
| 多邮箱 | 一 KOL 多邮箱 | 按 KOL + 规范化邮箱唯一，级联删除 |
| 项目评估 | 同一 KOL 在多个并行项目下独立评估适配度 | 项目代码 + KOL 唯一，适配度受 CHECK 约束 |
| 会话 | 邮件往来的聚合，承载意向研判结果 | FK 到 KOL 与分派运营；按营销活动索引 |
| 单封邮件 | 一封具体邮件 + 其 AI 分析结果 | 邮件 ID 唯一；遵循邮件线程协议字段 |
| 内部备注 | 运营在会话上的协作记录 | FK 到会话与运营 |
| 运营人员 | 协作主体 | 邮箱唯一；无密码列 |
| 发送审计 | 发信行为审计 | FK 到 KOL / 会话（可空） |

### 4.2 核心领域概念

| 概念 | 含义 |
|---|---|
| **大数据库** | 全量候选池，作为长期挖掘素材（含无邮箱账号） |
| **发信池** | 大数据库中"有邮箱"的子集晋升而来，是真正可触达的集合 |
| **Hot Lead** | 意向判定为高（或评分超过阈值）的会话，看板置顶 |
| **多项目评估** | 同一 KOL 可在多个业务项目下独立打分，互不覆盖 |
| **意向研判** | AI 对每封入站回信输出结构化判断，映射为会话状态 |

### 4.3 数据来源与去重策略

系统汇聚**三类异构来源**，每类有独立的去重键与覆盖策略：

| 来源 | 入口 | 写入目标 | 去重键 | 字段覆盖策略 |
|---|---|---|---|---|
| 全量候选清单（多列 Excel） | 上传 / CLI 推送 | 候选大库 + 发信池 + 多邮箱 | 平台 + 账号；邮箱 | **增量回填空字段**（不覆盖已有值） |
| 邮箱采集结果（多 preset Excel） | 上传 / CLI 推送 | 候选大库 + 发信池 + 多邮箱 | 平台 + 账号；邮箱 | **增量回填空字段** |
| 历史清洗名单（早期格式） | 上传 | 发信池 + 项目评估 + 多邮箱 | 邮箱 | **最新批次覆盖**（仅此格式） |

> 设计取舍：新版导入器统一采用"只填空"策略以保护人工已修正的数据；唯一例外是早期格式保留"覆盖"行为以兼容历史批次语义。

### 4.4 迁移治理

**结构演进的唯一受控入口是迁移工具**，遵循以下硬约束：

| 约束 | 说明 |
|---|---|
| ✅ 新表 / 新列 / 新索引 → 新建迁移 revision | 经自动生成 + 人工审查 + 升级 |
| ❌ 禁止运行时建表上生产 | 建表函数仅用于本地首次初始化与遗留 SQLite 兼容 |
| ❌ 禁止在遗留补列函数里加结构变更 | 补列函数只为老库做向后兼容，不再扩展 |
| ❌ 禁止手写 DDL 上生产 | 一切结构变更经迁移工具留痕 |
| ⚠ 新模型必须在模型注册表中 import | 否则迁移工具的自动比对看不到 |

迁移链呈线性单链：**基线快照 → 领域模型重构（拆文本大字段、引入多邮箱与项目评估、数据回填）→ 候选大库与可发信视图**。所有迁移应可正向升级、可回退一版；含数据回填的迁移回退时只还原结构、不还原数据。

> 遗留的 raw SQL 文件与一次性数据回填脚本是迁移工具接管前的产物，**不再新增**。

### 4.5 存储策略

- **开发环境**：嵌入式单文件数据库，零运维。
- **生产环境**：独立关系型数据库服务（容器化）。
- 切换通过单一配置项完成，ORM 层屏蔽差异（仅个别方言相关 DDL 需注意兼容）。

## 5. 运行架构

### 5.1 进程模型

```
┌─────────────────────────────────────────────────────┐
│              单一后端进程（ASGI）                    │
│                                                     │
│  ┌──────────────┐   事件循环（asyncio）             │
│  │ HTTP 路由    │                                   │
│  └──────┬───────┘                                   │
│         │                                           │
│  ┌──────┴───────────┐   ┌──────────────────────┐   │
│  │ BackgroundTasks  │   │  APScheduler（进程内）│   │
│  │ （请求级后台）   │   │  定时兜底同步         │   │
│  └──────────────────┘   └──────────────────────┘   │
│                                                     │
│  线程池：AI 画像回填（多 worker）                   │
└─────────────────────────────────────────────────────┘
```

- **单进程、事件循环驱动**：HTTP 请求、后台任务、定时任务共享同一进程。
- **无独立 worker / 无消息队列**：所有异步工作在进程内完成。

### 5.2 三类后台机制

| 机制 | 触发 | 用途 | 状态持久化 | 重启行为 |
|---|---|---|---|---|
| 定时调度器 | 周期性（可配间隔，最小 60s） | 兜底拉取外部邮件平台遗漏的回信，修补漏接的 webhook | 无 | 进程内，重启即重新计时 |
| 请求级后台任务 | 单条外部事件到达后 | 对该封回信跑意向分析 | 无 | 丢失，靠定时调度或人工补跑 |
| 线程池批量任务 | 运营在看板触发 | AI 画像批量回填 | 内存态任务表 | 丢失，靠幂等重跑补回 |

**幂等性是这套设计的基石**：因为任务不跨重启，所有任务都必须能在重启后被安全重跑而不产生重复或脏数据。去重靠稳定指纹（邮件 ID 优先，缺失时用内容哈希）；回填只填空字段；同步按历史指纹去重。

### 5.3 并发控制

- **定时任务单实例**：同一调度作业同时只允许一个实例运行（`max_instances=1`、`coalesce`），避免重叠拉取。
- **批量回填单并发**：同一时刻只允许一个画像回填批量任务，冲突时拒绝（返回 409），避免并发 AI 调用导致成本翻倍。
- **长耗时同步端点**：历史回信补拉端点是**同步执行**（不入后台），调用方需容忍较长耗时。

## 6. 业务流程架构

### 6.1 数据入库漏斗（候选 → 发信池）

系统有**两条入库路径**，最终都汇入同一"双写"核心：

```
 路径 A：内嵌采集器（Web UI 触发后台任务）      路径 B：外部数据文件（Excel）
   run_crawl(products)                            外部 xlsx
        │                                              ├── CLI 推送工具（判格式 + 重试）
        │                                              └── Web 上传
        ▼                                              ▼
   关键词发现 → about 抓取              格式探测：按表头特征路由导入器
   → 多平台扩展 → 邮箱 → MX                        │
        │                                              ▼
        ▼                                     统一导入入口 run_import(...)
   产出 candidate 行 dict                              │
        │                                              │
        └──────────────┬───────────────────────────────┘
                       ▼
              共享入库核心 upsert_candidates(rows, db, batch)
                       │
            ┌──────────┴──────────┐
            ▼                     ▼
      写候选大库            当行含邮箱时晋升
      （平台+账号去重，     ├─ 写发信池（邮箱去重）
       增量回填空字段）     └─ 写多邮箱（KOL+规范化邮箱去重）
```

**关键设计**：
- **双路径共用入库核心**：采集器（路径 A）产出 dict 列表后直接调 `upsert_candidates`；Excel（路径 B）经 `run_import` 解析后也调它。入库去重逻辑只有一份。
- **采集器内嵌**：路径 A 完全在系统内（`services/crawler/`），无需外部脚本或手工转文件。
- **CLI 与 HTTP 同一入口**：推送工具只是 HTTP 端点的瘦客户端包装，避免两套导入逻辑。
- **格式自适应**：导入器内置格式探测，按表头特征自动选择列映射与 preset。
- **字段截断保护**：所有变长字段按列宽截断，避免溢出错误。
- **数值解析**：粉丝数 / 播放量支持千 / 百万后缀解析。
- **多邮箱拆分**：单元格内多邮箱按多种分隔符切分，小写去重保序。

### 6.1.1 采集器流水线（路径 A 详解）

```
 [Web UI] 选产品 + 选项 → POST /crawler（后台任务，立即返回 job_id）
                              │
                              ▼
   阶段 1 发现：产品×关键词 → 平台搜索 → 频道 handle（并发 3，礼貌限速）
                              │
                              ▼
   阶段 2+3 扩展+邮箱：每频道抓 about →
        ├─ 解析标题/简介/订阅数/国家（平台声明优先，否则简介推断）
        ├─ 抽公开邮箱 + 商务信号识别（邮箱周 100 字符含 business/sponsor/…）
        └─ 多平台外链扩展（IG/TikTok/X，从简介与外链区块抽取）
        产品-国家白名单过滤（如某产品仅允许 UK）
                              │
                              ▼
   阶段 4 MX 校验：对邮箱域做 DNS MX 查询（线程池并发 30）
        MX 无效的行：邮箱不进发信池，账号仍入大数据库留档
                              │
                              ▼
   阶段 5 入库：upsert_candidates → 候选大库 + 发信池 + 多邮箱
                              │
                              ▼
   [前端每 2s 轮询 /crawler/status] → done 时展示统计
```

**抗反爬设计**：
- **可插拔 Fetcher 抽象**：抓取封装在 `Fetcher` 接口后（首期 `HttpxFetcher`）。将来要换无头浏览器渲染，只需新增 Fetcher 实现，业务解析与流水线不动。三阶段并发上限、请求间隔、UA 均可配。
- **住宅代理池**：数据中心 IP 几乎必被 YouTube 封。`Fetcher` 接受多个代理 URL，按 round-robin 轮换；遇到 403/429 自动切下一个代理重试（单 IP 被限流时整个池子继续工作）。代理池越大，单 IP 承压越分散。未配置则直连（仅适合本地开发或住宅网络直接出口）。
- **端点鉴权**：触发采集是带副作用的写入（真实抓取 + DNS + 写库），绝不能像只读看板那样公开。采集三端点强制请求头 token（恒定时间比对，与 webhook token 同模式），未配置/占位符返回 503 关闭端点。

### 6.2 邮件会话同步与意向研判

```
 外部邮件平台：发信 / 收信事件
        │
        ▼
 事件入口（webhook）── 鉴权闸：专用令牌校验（恒定时间比较）
        │                  ├─ 未配置 → 服务不可用
        │                  └─ 不匹配 → 拒绝
        │
        ├── 事件解析（发信 / 回信 / 自动回复，兼容多种事件命名）
        ├── 字段规范化
        ├── 去重：邮件 ID 优先，缺失则用内容哈希稳定指纹
        │
        ▼
 upsert：发信池 KOL / 会话 / 单封邮件
        │
        ▼
 请求级后台任务：对该封回信跑意向分析
        │
        ▼
 更新：邮件的 AI 分析结果（JSON）
       + 会话的意向 / 评分 / 摘要 / 状态
```

**兜底链路**（修补漏接的 webhook）：

```
 定时调度器（周期性）
        │
        ▼
 主动拉取外部邮件平台的营销活动回信
        │
        按历史指纹幂等去重
        │
        ▼
 对新增回信同步跑意向分析
```

**SLA 约束**：webhook 入口须在数秒内返回（满足外部平台回调超时要求），因此意向分析必须异步化。

### 6.3 Hot Lead 运营闭环

```
 看板（Hot Lead 优先 + 意向评分倒序，定时自动刷新）
        │
        ├── 选中会话 →「AI 补全画像」
        │       │  触发批量回填后台任务（线程池，单并发）
        │       │  抽取结构化画像字段 + 最低报价
        │       │  合并进邮件的 AI 分析结果（不动已有意向字段）
        │       │  前端定时轮询任务进度
        │       ▼
        │     生成结构化画像 + 报价，供运营决策
        │
        └── 选中会话 →「导出选中」
                │  构建报价工作簿
                ▼
              下载（支持非 ASCII 文件名）
```

### 6.4 意向 → 状态映射

AI 输出的意向标签 + 评分经映射函数转为会话状态：

| 意向标签 | 或评分条件 | → 会话状态 |
|---|---|---|
| 高意向 | 或评分 ≥ 高阈值 | **hot**（置顶） |
| 中意向 | 中区间 | warming |
| 低意向 | 低于中阈值 | open |
| 负向 | — | closed |
| 外出 / 自动回复 | — | 按规则降级 |

## 7. 外部集成架构

> 本节描述集成**方式与契约**，不涉及第三方服务的具体字段名。

### 7.1 外部邮件平台集成（适配层）

系统与外部邮件平台有**三个集成通道**，封装在独立适配模块，协议细节不外泄到领域层：

```
                  ┌─────────────── 适配层 ───────────────┐
                  │                                     │
  ① 事件推送  ◀───┤  webhook 入口（被动接收）           │
  （发信/回信）    │  - 专用令牌鉴权（恒定时间比较）     │
                  │  - 多事件命名兼容                    │
                  │  - 稳定指纹去重                      │
                  │                                     │
  ② 兜底拉取  ───▶│  定时轮询（主动修补漏接）           │
  （历史回信）     │  - 周期可配（最小 60s）              │
                  │  - 幂等去重                          │
                  │                                     │
  ③ 管理操作  ◄──▶│  REST 客户端（联系人 / 活动 / webhook 管理）│
  （联系人等）     │  - 凭证鉴权                          │
                  │  - 自检不返回密钥                    │
                  └─────────────────────────────────────┘
                                  │
                                  ▼ 规范化后的领域事件 / 数据
                          领域层（会话 / 邮件 / KOL）
```

**设计要点**：
- **被动 + 主动双通道**：webhook 是主路径（实时），定时轮询是兜底（修补漏接），两者共享同一去重逻辑。
- **协议隔离**：外部事件名、字段名的解析与归一化全部在适配层完成，领域层只看到规范化的领域事件。
- **凭证治理**：所有外部凭证走配置注入；连接自检端点只返回计数，绝不回显密钥。
- **启用可控**：定时同步需开关 + 凭证同时具备才启动。

### 7.2 AI 推理集成（适配层）

系统通过 **OpenAI 兼容协议**调用外部 AI 服务，封装为三个**职责分离**的独立服务：

| 服务 | 用途 | 输出契约 | 失败降级 |
|---|---|---|---|
| 意向研判 | 判断回信合作意向（**系统大脑**） | 严格结构化 JSON：意向标签、评分、报价、关键问题、时间线、摘要、建议动作 | 本地关键词规则 |
| 内容生成 | 基于近期内容生成冷邮件开场白 | 自然文本 | 占位文本 |
| 画像抽取 | 从回信抽取结构化画像 + 报价 | 多字段结构化数据 + 报价正则 | — |

**设计要点**：
- **协议兼容**：通过可配置的推理端点地址，可替换为任何兼容协议的服务（不绑定单一供应商）。
- **职责分离**：意向研判（要不要跟进）与画像抽取（KOL 是谁、报价多少）刻意拆为两个服务，避免耦合。
- **严格输出**：意向研判强制结构化 JSON 输出 + 低温度，保证可解析、可映射。
- **降级保活**：凭证缺失或调用失败时，全部退化为本地规则 / 占位，系统保持可用（但研判质量下降）。
- **成本控制**：历史重分析能力**故意只暴露为 CLI**（不开放 HTTP），避免误触发烧钱；批量回填任务**单并发**，避免并发翻倍成本。

### 7.3 安全边界

- **入站唯一鉴权闸**：外部事件入口的令牌校验是系统唯一在用的安全闸。
- **看板公开访问**：是有意设计（依赖网络层隔离），非遗漏。
- **日志防泄密**：HTTP 客户端与 AI 客户端的底层日志强制降到告警级别，避免外部凭证、邮件正文落盘。
- **发送安全阀**：相关配置仅作约束留存（本系统不发信）。

## 8. 前端架构

### 8.1 结构

```
入口 → 根组件 → 路由 → 主布局（侧栏 + 内容区）→ 页面视图
```

- **技术**：响应式框架 + 组件库 UI + 客户端路由 + HTTP 客户端。
- **形态**：单页应用（SPA），生产由静态文件服务器托管并反代 API。

### 8.2 页面与职责

| 页面 | 职责 | 架构要点 |
|---|---|---|
| 总览 | 全局概览 | — |
| Hot Lead | 运营主工作台 | 定时自动刷新；批量回填任务进度定时轮询 |
| 邮箱 | 会话列表 | 复杂查询的展示端（folder / 搜索 / 过滤 / 分页） |
| 会话详情 | 单会话往来 + 回复入口 | 从邮箱进入时侧栏保持高亮邮箱 |
| KOL 列表 | 发信池管理 + 批量操作 | — |
| 导入 KOL | 多格式上传 + 模板下载 | 两类来源分卡片；含字段规格说明 |
| 统计 | 意向分布等图表 | — |

### 8.3 API 访问层

- **单一 HTTP 客户端实例**：统一基础路径与超时。
- **响应拦截器**：统一剥离外层响应封装，业务代码直接拿负载。
- **按业务域分组导出**：每个业务域一组方法，页面只依赖分组接口而非裸 HTTP。

### 8.4 开发与构建

- **开发期代理**：开发服务器把 API 前缀代理到后端端口，规避浏览器跨域。
- **构建产物**：打包为静态资源，生产由静态服务器托管 + API 反代。
- **构建期注入**：少量前端所需的外部链接（如跳转到外部邮件平台收件箱）通过构建期变量注入。

## 9. 部署架构

### 9.1 部署形态

```
                        生产环境
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
   反向代理 / TLS     后端服务（ASGI）     关系型数据库
   （自动证书）        （单进程）          （持久卷）
        │                  │
        │                  └─── 后端进程内：定时调度 + 后台任务
        │
   静态前端资源（SPA）
```

- **全栈容器编排**：数据库、后端、前端、反向代理各为一个服务，同一网络互通。
- **TLS 终止于边缘代理**：边缘代理负责证书自动签发与 HTTPS 终止，转发明文到内部。
- **前端为静态托管**：前端服务本质是静态文件服务器 + API 反向代理。
- **数据持久化**：数据库与缓存类服务用命名卷持久化。

### 9.2 环境分层

| 环境 | 数据库 | 后端 | 前端 | 用途 |
|---|---|---|---|---|
| 本地开发 | 容器化数据库（仅起库）/ 嵌入式单文件 | 本机热重载 | 本机开发服务器（代理 API） | 日常开发 |
| 生产 | 容器化独立数据库 | 容器化单 worker | 容器化静态托管 + 边缘代理 | 对外服务 |

### 9.3 配置治理

- **分层加载**：生产环境文件 → 应用环境文件 → 进程环境变量（后者覆盖前者）。
- **占位符拒绝**：关键凭证配置含判定属性，会拒绝空值与明显的占位串（如 `change-me-*`），避免带着默认值上生产。
- **健康检查**：后端暴露轻量健康端点，供容器编排做存活探测。

## 11. 演进与风险

### 11.1 架构演进脉络

系统经历了三个阶段的架构演进，当前形态是演进的结果：

1. **单体采集工具期**（已剥离）：独立的数据采集端，产出结构化文件供下游。
2. **中台成型期**：确立"外部邮件平台同步 + AI 研判 + Web 协作"的中台形态，引入 Webhook + 定时兜底 + 后台研判。
3. **数据治理期**：把文本大字段拆解为结构化领域模型，引入多邮箱、多项目评估，确立迁移工具为结构演进唯一入口，沉淀候选大库作为长期资产。
4. **采集回归期**：把采集能力从外部工具重新内嵌回系统（`services/crawler/`），消除"外部脚本产 JSON → 手工转 xlsx → 推送"的断链；Web UI 触发、后台任务、进度可见；抓取层抽象为可插拔 Fetcher 接口，业务规则（关键词/国家白名单/商务信号识别/正向种子）平移保留。

### 11.2 已识别的技术债与风险

| 项 | 影响 | 处置方向 |
|---|---|---|
| 运行时建表与遗留补列函数仍存在 | 与迁移工具并存，易误用 | 新结构坚决走迁移工具；补列函数不再扩展 |
| 任务状态为内存态 | 进程重启丢失进行中任务 | 靠幂等重跑兜底；规模化时需引入持久化任务队列 |
| 看板鉴权为死代码 | 想加鉴权时会崩（配置字段缺失） | 要么补齐配置并启用，要么删除 |
| 遗留的外部供应商集成模块 | 死代码，增加认知负担 | 可清理 |
| 无前端测试 / 端到端测试 | 回归靠人工 | 视团队规模补齐 |
| 长耗时同步端点 | 高负载时阻塞 | 视需要改为后台任务 |
| 根目录冗余文档副本 | 信息源不一致 | 以 docs/ 为准，清理副本 |

### 11.3 适用性与边界

- **适用**：中小规模 KOL 外联团队、单实例部署、对外部邮件平台有 webhook 能力。
- **不适用（当前架构）**：超大规模并发、跨进程持久化任务、多租户隔离、强一致分布式场景——这些需要引入消息队列、独立 worker、租户隔离层。
